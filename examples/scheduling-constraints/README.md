# 일정 최적화: 목적값보다 제약 만족을 먼저

## 요구와 실행
작업별 시간·가능 설비·선행 작업·정비 구간을 만족하며 완료 시각을 최소화한다.
```bash
python3 schedule.py
python3 -m unittest discover -s tests -v
```
시간 구간은 [start,end)다. 이전 작업이2에 끝나면 다음 작업은2에 시작할 수 있다.
정비도 같은 규칙이다. 모든 작업은 양의 정수 기간, 설비 용량1, 중단 없이 수행한다.

## 독립 정답
J2는3시간이고 그 뒤 J3가1시간이므로 makespan의 하한은4다. J1은 A에서0~2,
J2는 B에서0~3, J3는 A에서3~4로 하한을 달성한다. A의2~3 정비에도 위반이 없다.
solver는 작은 순서/설비 조합을 전수 탐색한다. `validate`는 solver의 배치 로직을 재사용하지 않고 결과 제약을 별도로 검사한다.
고의 결함은 A를0시부터 이중 사용해 빠른 일정을 만든다. makespan만 검사하면 놓치는 결함이다.

## 검사·계측·진단
필수: coverage, 허용설비, 기간, 선후행, 정비, 설비 중복, 납기 및 불가능 사례. 임의의 랜덤 일정 대량 생성은 우선하지 않는다.
CLI는 makespan·작업수·실행시간과 제약 위반 목록을 제공한다. 먼저 위반 종류를 좁히고 그 뒤 목적값을 비교한다.
새 목적함수를 추가하면 제약 검사에 더해 손계산 가능한 tiny optimum과 비교한다.

## 사용자가 이해할 한계
이 전수 탐색은 n! 및 설비 조합 때문에 최대7작업의 학습용이다. 대규모 최적화 권장이 아니다.
큰 과제에서는 규모·시간 제한을 보고 휴리스틱/solver를 선택하고 이 작은 oracle로 교차 검사한다.
휴리스틱 결과는 검증된 feasible이라고 말할 수 있어도 최적성 증거 없이 optimal이라고 하지 않는다.
사용자는 JSON 일정을 시간순으로 읽고 J3가 선행 작업 뒤에 시작하는지, 정비와 겹치지 않는지 확인한다.

`stage_summary`는 단계 설명이며 계측된 span이 아니다. 공통 verify runner의 trace.json은 검사 명령 단위 span을 기록한다.
