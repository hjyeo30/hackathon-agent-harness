# 계획서 예시 — 수율 조회와 다운로드

이 파일은 합성 연습 과제의 계획 기준선이다. 실제 과제에서는 원문 README와 사용자 답변을
근거로 다시 작성한다. 아직 하지 않은 사용자 확인을 완료로 기록하지 않는다.

## 목표와 필수 조건

W1. CSV를 입력해 전체 수율을 계산한다.
W2. 설비·기간으로 조회할 수 있다.
W3. 다운로드 내용은 마지막으로 완료된 조회 조건과 일치한다.
W4. 입력 오류를 성공으로 표시하지 않는다.
W5. 빠른 연속 요청에서도 마지막 요청만 화면에 반영한다.

## 근거와 결정

- 예제 fixture A:9/10, B:1/90. 전체 수율은 10/100=10%.
- UI, API, 다운로드가 같은 필터 의미를 사용한다. 날짜 양끝 포함.
- 중복 batch와 0 분모는 오류. 필터 결과가 없으면 미정(null), 0%와 구분.
- 처음에는 stateless JSON API를 사용한다. 매 요청에 CSV를 보내며 1 MiB 제한을 둔다.
- 저장/인증이 요구되지 않아 DB와 JWT를 추가하지 않는다.
- 업로드 파일명·내용은 로그에 저장하지 않고 행 수와 단계·확인 ID만 남긴다.

## 전문가 관점에서 확인할 부분

1. 비율의 합산 기준이 결과를 크게 바꾼다. 필수: 손계산 fixture로 검증.
2. 늦은 응답이 최신 결과를 덮을 수 있다. 필수: 요청 소유권과 오류/선택 변경 시 무효화.
3. CSV 다운로드를 스프레드시트로 열 수 있다. 필수: 사용자 문자열의 formula 해석 방지.

실제 과제에서는 사용자에게 수율 정의/0 분모/날짜 정책을 질문한다. 이 예제의 정책을
사용자가 실제로 선택한 것처럼 기록하지 않는다.

## 묶음과 관측

A. parse→집계→API: golden·입력 경계·HTTP. parse 실패 위치, 입력/출력 행 수.
B. UI 업로드→조회→export: 브라우저에서 수치와 파일을 직접 확인. 응답 trace_id 연결.
C. 오류·연속 요청 회귀: 이전 성공 지우기, 입력 변경 시 다운로드 무효화, 오래된 응답 무시.

각 묶음을 구현자→검토자→메인의 직접 사용 순서로 확인하고, 사용자가 첫 전체 흐름을
체험한 뒤 다음 기능으로 넘어간다. 이번 저장소 제작처럼 전체 범위가 일괄 승인되면
그 승인 범위 안에서 진행하며 사용자 체험 완료를 꾸미지 않는다.

## 검사 선택

작은 계산/입력은 Python 단위 검사, 실제 HTTP는 통합 검사, 업로드/다운로드/경쟁 상태는
Playwright로 검사한다. 화면 스타일 수정에 전체 알고리즘 예제를 재실행하지 않는다.
같은 실패를 고치면 같은 재현과 영향을 받는 인접 검사만 다시 실행한다.

## 의도적으로 제외

대규모 streaming, 영구 저장, 사용자 계정, 외부 API, 실시간 설비 연결, 전체 브라우저 조합.
이 중 하나가 실제 요구사항이면 계획을 바꾸고 해당 경계의 검증을 추가한다.
