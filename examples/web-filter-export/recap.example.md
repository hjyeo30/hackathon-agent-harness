# Recap 예시 — 실제 확인 상태에 맞춰 작성하기

다음은 합성 예제를 위한 **설명 구조**다. 사용자가 아래 행동을 했다고 주장하는 기록이 아니다.
작업 중 본인 확인 후 수정해서 사용하며, AI 사용이 금지되는 후속 서술형 단계에서 호출하지 않는다.

## 서비스의 핵심 동작과 이를 확인한 방법은?

입력 CSV의 양품 수와 검사 수를 합산해 전체 수율을 계산하고, 설비·기간으로 필터해
결과를 보여주며 동일 조건의 CSV를 다운로드한다. A 9/10, B 1/90 입력의 전체 수율이
10%임을 손계산 oracle로 삼는다. 계산 함수, 실제 HTTP, 업로드·다운로드 브라우저 경로는
서로 다른 경계를 확인한다. **실제로 실행한 검사만** 설명에 포함한다.

근거: fixtures/unequal-batches.csv, tests/test_server.py, browser-tests/app.spec.js,
실제 검증 실행의 report와 events. 테스트 코드가 존재하는 것과 실행한 것은 다르다.

## AI 제안을 직접 확인하거나 수정한 부분은?

기록에서 실제 사례를 고른다: 제안 내용→어떤 의심/입력으로 확인했는지→관찰값→수정 이유→재검증.
가상 예: 배치별 비율 평균 제안을 손계산 fixture로 반박하고 전체 양품/검사 비율로 수정.
단, 실제 작업에서 이 제안·수정이 없었다면 이 이야기를 사용하지 않는다.

## 왜 이런 테스트 입력인가?

크기가 같은 배치만 사용하면 잘못된 단순 평균도 맞아 보일 수 있다. 분모 10과 90을 사용하면
잘못된 평균 약45.56%와 정답10%가 분리된다. 날짜 한쪽 경계, 빈 결과, 잘못된 수량은 각각
필터 off-by-one, null과 0 혼동, 실패를 성공으로 바꾸는 문제를 드러낸다.

## 오류 원인을 어떻게 좁혔는가?

UI의 확인 ID를 서버 trace_id와 연결하고 decode/parse/filter/aggregate/export 단계 중 처음
실패한 위치를 본다. API는 맞고 DOM만 틀리면 표시·비동기 상태를, export만 틀리면
다운로드 필터를 확인한다. 실제 run 기록이 없다면 방법을 설명할 수는 있어도 경험했다고 말하지 않는다.

## 남은 한계는?

작은 CSV용 stateless 예제이며 1 MiB 요청 제한이 있다. 인증·영구 저장·대규모 데이터 처리를
검증하지 않았다. 다음 요구가 들어오면 그 기능의 실패 비용과 입력 규모를 근거로 확장한다.

## 행위 주체 기록

- Agent가 실행한 명령: 실제 report 경로를 기입.
- 사용자가 직접 조작한 동작: 사용자 확인이 있을 때만 기입.
- 사용자가 선택한 업무 정책: 사용자 답변이 있을 때만 기입.
- 확인하지 못한 점: NOT RUN/BLOCKED와 이유를 유지.
