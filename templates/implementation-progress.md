# 구현 진행 기록 작성 틀

원래 계획은 기준선으로 보존한다. 명령마다 일지를 쓰지 않고 기능 묶음·실질적 결정·
실패 원인·검증 시점에 기록한다. 아래 예시는 형식 설명이며 실제 수행 기록이 아니다.

## 묶음 1 — 진행 중 / 구현됨 / 검증됨 / 사용자 확인됨 / 차단됨

- 요구사항: R1, R2
- 결과: 사용자가 지금 할 수 있는 동작을 기술한다.
- 변경: 관련 파일과 경계만 적는다.
- 계획 차이: 없음 또는 새로운 증거, 선택, 이유와 범위 영향.
- 검증: 명령, 입력, 기대/관찰, PASS/FAIL/BLOCKED/NOT RUN.
- 관측: run ID, 코드/빌드 식별, 로그·메트릭·트레이스 경로.
- 실패 원인: 확인됨/추정됨을 구분하고 상세 failure record로 연결한다.
- 인간/AI: agent가 실행한 것, user가 직접 확인한 것, 결정한 것을 구분한다.
- 사용자 확인: 대기 또는 실제 사용자 피드백과 시점. 침묵은 확인이 아니다.
- 다음: 합의된 다음 묶음 또는 결정을 기다리는 질문.

## 결정 변경 예시

처음에는 전체 CSV를 읽으려 했으나 대표 입력에서 메모리 제한을 넘었다.
필요 열만 읽고 분할 가능한 합계/개수로 집계하도록 변경했다. 결과는 작은 정답
fixture와 전체 처리 결과 비교로 확인한다. 실제 측정값과 명령이 없으면 이 문장을
수행 사실로 복사하지 않는다.

## 마감

필수 조건별 완료/검증/미검증 상태, 현재 증거, 제출 경로, 알려진 한계를 적는다.
성공 결과만 남기지 말고 최종 판단에 영향을 준 실패와 기각 이유도 남긴다.
