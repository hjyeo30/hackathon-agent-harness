# TypeScript/JavaScript 작업에서 필요한 판단

## 프로젝트 적응

package.json scripts, lockfile, Node/runtime, framework, build/test 구성을 확인하고 그대로
사용한다. npm/pnpm/yarn lock을 중복 생성하지 않는다. 실제 실행 환경과 다른 API를
기억만으로 호출하지 말고 현재 버전의 공식 문서를 확인한다.

타입 검사, 빌드, 런타임 테스트, 브라우저 행동은 서로 다른 증거다. `tsc` 통과만으로
사용자 흐름을 완료 처리하지 않는다. 타입 오류를 any/강제 cast로 무작정 덮지 않는다.

## 외부 입력과 숫자

TypeScript 타입은 런타임의 JSON·폼·파일을 검증하지 않는다. 입력 경계에서 실제 shape,
누락/null, 범위와 의미를 확인한다. 프레임워크의 기존 validator가 충분하면 새 라이브러리를
추가하지 않는다. 검사 후 내부 경로에서 같은 전체 검증을 반복할 필요는 없다.

Number의 정밀도와 큰 정수 ID, 금액·비율 단위를 확인한다. 선행 0이 있는 ID는 숫자가
아닐 수 있다. NaN, 빈 문자열 숫자 변환, 날짜 파싱과 시간대 경계는 touched input에서
검사한다. 숫자를 보기 좋게 포맷하는 것과 계산하는 경계를 분리한다.

## 비동기와 상태

A 요청 후 B 요청을 했는데 A가 늦게 도착하면 최신 선택을 덮는지 확인한다.
취소/요청 ID/상태 소유권 등 기존 패턴으로 해결하고 고정 sleep을 쓰지 않는다.
Promise를 기다렸는지, rejection이 호출자에게 드러나는지, loading/error 상태가
종료되는지 본다. 무한 재시도나 같은 부작용의 중복 호출을 넣지 않는다.

UI 컴포넌트마다 별도 서버 상태를 복제하면 불일치가 생길 수 있다. 현재 구조에서
가장 작은 단일 소유권을 선택한다. 테스트를 위해 내부 setter를 호출해서 실제 이벤트
경로를 우회하지 않는다. DOM은 role/label 등 안정적인 사용자 의미로 조작한다.

## 자원과 알고리즘

큰 JSON/CSV를 브라우저에 모두 올리는지, 반복 렌더/전체 scan/불필요한 복사가 있는지
측정한다. 메인 스레드의 CPU 작업과 네트워크 대기를 구분한다. 작은 데이터부터 Worker,
streaming, cache를 추가하지 않는다. 서버와 브라우저에서 자료 구조/메모리 비용이 다르다.

## 검증과 관측

순수 로직은 단위/golden 또는 의미 있는 property, API는 계약/통합, UI는 핵심 E2E를
고른다. fast-check는 올바른 불변조건과 입력 범위가 있을 때 사용한다. 외부 경계 mock으로
오류·경쟁 조건을 검사하되 실제 서버와의 E2E를 대신했다고 표현하지 않는다.

request/action ID, 상태 전이, API status/error, 처리 시간과 데이터 수를 연결한다.
콘솔만 보지 말고 네트워크와 서버 로그를 함께 읽는다. 브라우저 성능 문제는 실제
측정으로 병목을 확인한다. 캡처/trace 허용과 로컬 보존 조건을 따른다.
