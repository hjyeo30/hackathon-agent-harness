# 웹앱과 대시보드

## 계획에서 확인

누가 어떤 입력으로 어떤 결정을 하는가? 기존 화면/컴포넌트/API를 재사용할 수 있는가?
필수 흐름을 한 줄로 그린다: 입력→요청→계산/저장→표시/다운로드.
빈 상태·로딩·실패 상태가 실제 과제에서 필요한지 확인한다. 로그인/DB는 요구에 있을 때만.
기간 필터라면 경계 포함·시간대·다운로드에 동일 적용되는지를 합의한다.

## 실행과 직접 조작

실제 startup 명령, 포트, ready 조건, 코드/build identity를 확인한다. 서버 소유자를
한 명 정한다. 제공 Browser 접근에는 환경에서 요구하는 bind/포트를 사용한다.
AI는 Playwright CLI/MCP 등 하나의 도구로 입력·클릭·이동을 실제 수행한다.
사용자가 보는 동작은 내부 setter나 test-only API 호출로 대체하지 않는다.

관찰: DOM, 실제 화면, 콘솔 오류, 요청/응답, 서버 로그, 저장/다운로드 결과.
화면이 예쁘거나 API가 200인 것만으로 성공이 아니다. API/UI 값이 같아도 둘 다 틀릴
수 있으므로 작은 독립 정답을 쓴다. 실제 사용성은 사람이 확인한다.

## 높은 가치의 입력과 회귀

| 상황 | 입력/행동 | 독립 판정 |
|---|---|---|
| 집계 | 크기가 다른 두 배치 | 손계산값 |
| 필터 | 시작/끝 경계와 범위 밖 행 | 포함 규칙 |
| 비동기 | A 요청 후 B 요청, A가 늦게 응답 | 마지막 사용자 선택 B 유지 |
| 저장 | 입력→저장→새로고침/재조회 | 저장된 값 |
| 다운로드 | 필터 설정→파일 받기→파싱 | 화면/계약/원자료의 일치 |
| 오류 | 허용되지 않는 파일 또는 API 오류 | 오류가 보이고 가짜 성공 없음 |

새 필터는 기존 전체 조회/다운로드의 주요 회귀도 확인한다. CSS 클래스·구현 함수명
대신 role/label/testid 등 안정적인 사용자 경계를 사용한다. 고정 sleep보다 조건을 기다린다.
수십 개의 유사 클릭 테스트보다 핵심 경로와 실제 위험 경계에 집중한다.

## 계측과 피드백

request ID로 UI action→API→계산 span을 연결하고 상태/응답 시간/입력 행 수를 적는다.
렌더링 지연인지 서버 지연인지 분리한다. performance trace·screenshot은 허용되는
환경에서만 저장하며 외부 업로드하지 않는다. 필수 경로가 바뀌면 프로젝트 검증 recipe도
갱신하고 실제 다시 조작한다. 도구 선택은 [catalog](../tools/catalog.md)를 참고한다.

[Playwright best practices](https://playwright.dev/docs/best-practices)는 사용자에게
보이는 행동과 테스트 격리를 강조한다.
