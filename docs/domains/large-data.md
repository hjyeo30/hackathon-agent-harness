# 대용량·메모리·속도·자료구조

## 계획에서 수치를 확인

파일 크기/행 수/열/자료형, 필요한 결과, 사용 가능한 메모리/CPU/디스크/시간,
중간 join/sort/group 결과 크기를 확인한다. 파일이 RAM보다 작아도 파싱·문자열·복사·
중간 결과 때문에 메모리를 넘을 수 있다. 병렬화는 메모리 계획을 대신하지 않는다.

먼저 필요한 열만 읽고 기존 자료구조를 확인한다. 전체를 메모리에 올려도 충분하면
복잡한 분산 체계를 추가하지 않는다. 그렇지 않으면 연산이 정확히 분할 가능한지 판단한다.

| 연산 | 분할 시 확인할 것 |
|---|---|
| 합계/개수 | 부분 합/개수를 합칠 수 있음, overflow/단위 |
| 평균/비율 | 부분 평균의 평균이 아닌 합계와 분모를 합침 |
| 중복 제거 | chunk 사이 중복도 처리해야 함 |
| 정렬/중앙값/분위수 | 단순 부분 결과 결합으로 정확하지 않을 수 있음 |
| JOIN | key cardinality와 중간 결과 폭증 |
| 시계열 window | 경계의 이전 상태를 유지해야 함 |

## 알고리즘과 자료구조

입력 크기 N과 필요한 연산을 쓰고, 반복 scan·nested loop·정렬·조회 비용을 본다.
set/dict 인덱스는 반복 조회를 줄일 수 있지만 메모리를 쓴다. 실제 필요 없는 캐시,
DB, scheduler, queue를 넣지 않는다. 작은 참조 구현으로 최적화 전후 정답을 비교한다.

## 관측과 실험

대표 입력, N/2N 입력, 편향된 키 분포 등 실제 위험을 고른다. 입력 크기, wall time,
처리량, peak memory의 측정 방식/단위/OS, output count/정답을 함께 기록한다.
Python tracemalloc은 전체 프로세스 RSS가 아니다. 한 번의 실행 비율로 Big-O를 증명하지 않는다.
캐시·warmup·디스크·다른 프로세스 영향을 구분하고 지나치게 작은 시간 차이를 성능 개선으로 주장하지 않는다.

OOM이 나면 증거를 보존하고 working set/중간 복사를 줄이는 방향을 조사한다.
처리 실패를 입력 일부 생략이나 샘플링으로 숨기지 않는다. 샘플 분석을 선택했다면
범위와 대표성 한계를 사용자와 합의한다.

## 회귀와 회복

분할 결과와 전체 작은 oracle 비교, chunk 경계의 중복/window 입력, 마지막 불완전
chunk를 검사한다. cheap하고 안전하게 다시 돌릴 수 있으면 checkpoint를 만들지 않는다.
비싼 작업의 재개는 input identity와 durable output 이후 checkpoint라는 조건을 정의한다.
진행률 로그는 전체 행을 출력하지 않고 partition 단위로 남긴다.
