# API·인증·상태 변경

## 설계 질문

사용자/호출자는 누구이며 누구의 자료를 읽고 바꾸는가? 실제 인증 요구가 있는가?
기존 프레임워크의 인증/세션 기능이 있는가? 세션 만료·로그아웃·권한 경계가 무엇인가?
JWT라는 용어를 사용자에게 요구하거나 기본 답으로 채택하지 않는다.
단순 로컬 도구에 불필요한 계정 시스템을 추가하지 않는다.

인터페이스에는 필드 의미, 단위, null/누락, 최대 크기, 성공/실패, 변경 부작용을 정의한다.
검증은 신뢰가 바뀌는 입력 경계에서 한다. TypeScript 타입만으로 외부 JSON이 검증되지는
않는다. API 스키마 일치가 업무 정답을 대신하지도 않는다.

## 재시도와 멱등성

같은 요청이 다시 올 수 있는지, 서버가 처리했지만 응답만 유실될 수 있는지 확인한다.
안전한 재시도에는 안정적인 요청 ID와 중복 정책이 필요할 수 있다. 같은 ID에 다른
payload가 오면 계약대로 충돌을 드러낸다. 무조건 성공 캐시를 반환하지 않는다.
재시도는 transient failure와 안전한 부작용에 한정하고 시도/총시간을 제한한다.
validation error를 재시도로 고치려 하지 않는다. 여러 계층이 각각 재시도해 폭증하지 않게 한다.

## 테스트 선택

- 정상 입력으로 실제 응답과 저장 결과를 확인한다.
- 누락/타입 오류/크기 경계는 실제 계약을 기준으로 최소 대표 사례를 고른다.
- 권한이 있으면 다른 사용자의 자료 접근·변경 거절을 검사한다. 인증 성공만으로 권한을 증명하지 않는다.
- 동일 이벤트 반복 후 부작용이 한 번인지 읽어 확인한다.
- 실패 전/후 commit 경계를 검사하되 실제 partial-failure 위험이 있을 때만.
- 외부 API mock으로 오류 처리를 검사하고, 실 서비스 연결 여부는 별도 표시한다.

Schemathesis는 OpenAPI/GraphQL 입력 경계 탐색 후보지만 업무 규칙 oracle과 별도다.
전체 API fuzzing은 작은 수정의 기본 의무가 아니다.

## 관측

operation/request ID, route, status/error category, retry count, duration, durable write
결과를 연결한다. 인증 값·쿠키·토큰·사용자 원문은 기본 로그에 넣지 않는다.
timeout이면 연결·대기·처리·저장을 분리해서 어느 단계가 느린지 조사한다.
