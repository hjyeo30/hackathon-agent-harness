# 실패 원인을 좁히는 순서

## 관찰 → 가설 → 판별 → 수정 → 같은 검사

1. 기대와 실제 차이를 한 문장으로 쓴다. “안 됨” 대신 입력/행동/잘못된 출력.
2. 현재 앱, 빌드, 데이터, 설정, 실행 명령이 맞는지 확인한다.
3. 입력에서 출력으로 경계를 따라가며 첫 어긋남을 찾는다.
4. 가능한 원인마다 다른 결과를 예측하는 작은 실험을 정한다.
5. 새 증거로 지지·기각·미결을 기록한다.
6. 원인에 맞는 작은 수정 후 동일 입력으로 재검사한다.
7. 인접 회귀 위험을 확인하고 사용자에게 실패와 수정 이유를 설명한다.

## 분류

| 현상 | 먼저 확인 | 부적절한 대응 |
|---|---|---|
| 브라우저 연결 불가 | 포트, ready, bind, 서버 종료 | 프론트 전체 재작성 |
| 테스트가 0개 | discover 경로와 파일명, runner 결과 | 초록색 exit만 믿고 완료 |
| UI만 틀림 | API 값, 상태 갱신, 포맷, 응답 순서 | DB부터 변경 |
| API/UI 함께 틀림 | 작은 oracle, 입력 정책, 집계 단계 | 서로 같은 값이니 통과 |
| OOM | 입력·중간 크기, peak 측정 | 무작정 병렬 worker 추가 |
| 불규칙한 실패 | 공유 상태, 시간, 순서, 외부 응답 | 고정 sleep/무한 재시도 |
| 저장 성공 후 값 없음 | commit/쓰기/읽기 경계 | 성공 메시지 검사를 추가 |
| trace 끝에서 timeout | 대기/처리/I/O별 시간 | 모든 timeout을 크게 변경 |

## 중단 기준

동일 실패에 새 증거 없이 패치만 반복되면 코드 수정을 멈추고 재현을 줄인다.
설치·도구 제약이면 필요한 조건과 시도한 명령을 보고한다. 무관한 fallback으로
결과를 꾸며내지 않는다. 사용자 판단이 필요하면 추천안/대안/현재 영향과 함께 묻는다.

[실패 기록](../../templates/failure-analysis.md)에 근거를 남긴다. “근본 원인”이라는
표현은 판별 실험이나 명확한 코드 경로가 뒷받침할 때 쓴다. 추정은 추정으로 남긴다.
