# 실제 작업을 설명하는 recap

## 언제 쓰나

사용자가 recap/복습/예상 질문을 요청하면 작업 결과와 판단 근거를 정리한다.
AI 사용이 허용된 과제 작업 단계의 학습용이다. 후속 서술형 등 AI 금지 단계에
사용할 답안을 제공하는 기능으로 운영하지 않는다. 예상 질문은 연습 후보다.

## 기록에서 뽑을 순서

원래 필수 조건 → 실제 코드의 핵심 흐름 → 중요 결정/수정 → 실행 증거 → 사용자
피드백 → 남은 한계. 구현자의 자신감이나 계획의 미래형 문장을 수행 사실로 바꾸지 않는다.

| 행위 | 올바른 표현 | 피할 표현 |
|---|---|---|
| agent가 테스트 실행 | AI가 해당 명령으로 확인했다 | 내가 직접 테스트했다 |
| user가 보고서만 읽음 | 결과 보고를 검토했다 | 앱에서 모든 기능을 눌렀다 |
| user가 직접 사용 | 실제 확인한 입력/동작을 적는다 | 기록 없는 추가 확인을 확대 |
| user가 정책 결정 | 결정 내용과 이유를 적는다 | AI가 고른 것을 user 선택으로 변경 |

## 예상 질문 선별

실제로 근거가 많은 5–8개를 고른다. 짧은 과제면 더 적어도 된다.

1. 핵심 기능은 어떤 입력을 받아 어떤 결과를 만드는가? 무엇으로 확인했는가?
2. AI 제안 중 직접 확인/수정한 것은 무엇이고 이유는 무엇인가?
3. 구현 방법을 왜 선택했는가? 실제로 검토한 대안은 무엇인가?
4. 정상 입력 외에 어떤 경계를 확인했으며 왜 그 입력이 중요한가?
5. 실제 실패를 어떻게 재현하고 어느 단계가 원인임을 확인했는가?
6. 수정 후 같은 문제가 해결되고 기존 동작이 유지됨을 어떻게 확인했는가?
7. 제한 시간에 무엇을 먼저 하고 무엇을 남겼는가?
8. 결과가 뒷받침하지 못하는 주장과 남은 한계는 무엇인가?

각 카드는 3–5문장 답변, evidence 위치, 추가 질문, 피해야 할 과장을 포함한다.
수치·성능·도구 이름을 외우게 하기보다 입력을 바꾸면 결과가 왜 달라질지 설명한다.

## 가상 예시 — 실제 수행 기록이 아님

질문: 전체 수율을 어떻게 확인했나요?

답변: “전체 양품 수를 전체 검사 수로 나누도록 정의했습니다. 배치 크기가 다르면
배치별 비율의 평균은 잘못될 수 있어, 9/10과 1/90을 합친 결과가 10%인지 확인하는
작은 입력을 사용했습니다. 계산 함수와 실제 사용자 입력 경로는 별도의 검증입니다.
화면까지 실행하지 않았다면 계산 검사만 확인했다고 설명하겠습니다.”

추가 질문: 분모가 0인 배치는 왜 그 정책으로 처리했나요?
피할 과장: 모든 데이터/화면/성능을 검증했다고 말하기.

## 기록이 없을 때

부족한 사실을 명시한다. 허용된 작업 시간 안이라면 사용자가 직접 해볼 작은 조작과
결과 예측을 제안한다. recap만 요청받았는데 코드를 바꾸거나 전체 테스트를 돌리지 않는다.
