# 필요한 테스트를 고르는 법

## 네 가지 서로 다른 축

| 축 | 종류 | 의미 |
|---|---|---|
| 검사 범위 | 단위·통합·API 계약·E2E | 어느 경계를 실제로 통과하는가 |
| 목적 | 새 기능·회귀·특성화·성능 | 무엇을 확인/보존하려는가 |
| 정답 기준 | golden·불변조건·변형 관계·참조 구현·human rubric | 맞다고 판단하는 근거 |
| 입력 전략 | 대표·동등 분할·경계·속성 생성·오류 주입·상태 전이 | 어떤 실패를 드러낼 입력인가 |

회귀는 별도 계층이 아니다. 하나의 검사가 “경계값을 쓰는 단위 회귀 테스트”일 수 있다.
종류별 폴더를 전부 만들거나 테스트 개수를 목표로 삼지 않는다.

## 추가하기 전 다섯 질문

1. 어떤 요구사항이나 실제 버그를 다루는가?
2. 어떤 잘못된 구현에서 실패해야 하는가?
3. 왜 이 입력인가? 범위·동등 클래스·경계·상태 중 무엇을 대표하는가?
4. 기대값은 원자료/규칙/손계산 등 어디에서 왔는가?
5. 가장 낮으면서 필요한 경계를 실제 통과하는 검사 수준은 무엇인가?

기대값을 현재 구현의 출력으로 그대로 만들면 같은 오해를 고정할 수 있다.
골든 파일도 최초 정답 근거가 필요하다. snapshot 갱신은 의미 검토를 대신하지 않는다.

## 변경별 배분

| 변경 | 먼저 할 것 | 더 할 조건 |
|---|---|---|
| 계산/파서 추가 | 작은 독립 정답 + 중요한 입력 경계 | 입력 공간이 넓고 불변조건이 분명하면 property |
| 상태/저장 | 실제 저장/읽기 통합 | 재시도·중단·동시성이 실제 계약에 있을 때 |
| 웹 흐름 | 핵심 사용자 경로 하나 + 내부 계산 검사 | 요청 경쟁·권한·오류 화면 등 touched risk |
| 버그 수정 | 최소 reproducer를 회귀로 보존 | 영향받는 기존 동작 |
| 리팩터 | 기존 입력/출력 특성화 | 현재 특성이 버그라면 요구사항으로 기대값 교정 |
| 성능 | 같은 입력·정답 보존·전후 실측 | 큰/편향 입력과 자원 경계 |
| 문서/스타일 | 실제 내용/화면 확인 | 동작하는 명령/설정이 바뀌면 해당 smoke |

변경 전 기존 실패를 기록한다. 버그가 재현 가능한 순수 로직이면 test-first가 유용하다.
이미 같은 실패를 잡는 검사가 있으면 중복 추가하지 않는다. UI 탐색·일회성 분석·
문서 수정에 모든 TDD 단계를 강제하지 않는다.

## 수율의 작은 oracle

9/10과 1/90의 전체 수율은 10/100=10%다. 비율의 단순 평균은 약 45.56%이므로
이 입력은 두 구현을 구분한다. 모든 배치 크기가 같은 랜덤 입력만 쓰면 오류가 숨는다.
0 분모, 빈 입력, 음수, 양품>전체, 중복 ID는 업무 정책을 먼저 정한 뒤 검사한다.

행 순서를 바꿔도 합계가 같은 것은 순서 무관 집계의 변형 관계다. 시계열·우선순위
처리에 무조건 적용하지 않는다. 두 chunk의 평균을 평균내는 것도 전체 평균과 다를 수 있다.

## 속성·오류·상태

속성 기반 생성은 입력 범위와 참이어야 하는 성질을 명확히 한 뒤 사용한다.
실패 입력을 축소·보존해 재실행 가능하게 만든다. seed 고정만으로 대표성은 생기지 않는다.
확률적 모델의 성능은 하나의 deterministic 테스트로 증명하지 않는다.

오류 주입은 해당 경계를 실제로 통과해야 한다. 응답 503을 주입했다면 재시도 횟수뿐
아니라 최종 상태·중복 부작용을 본다. 외부 mock을 통한 UI 검사는 실제 외부 통합과 다르다.
상태ful 기능은 create→retry→read, submit→cancel 등 의미 있는 전이를 고른다.

## 검증기 자체를 확인

핵심 oracle은 알려진 잘못된 구현/결과를 탈락시키는지 작게 확인한다. 모든 코드에
mutation framework를 설치할 필요는 없다. 테스트가 호출하는 코드 경로와 실제 사용자
경로가 다른지, 0개 검사/skip/xfail이 PASS를 꾸미는지 확인한다.

## 재검증 범위와 멈출 때

수정 직후 동일 reproducer → 영향받는 인접 회귀 → 필요할 때 통합/전체 검사를 실행한다.
새 코드·환경 변화·실패·미해결 위험이 없으면 넓은 검사를 반복하지 않는다. 불규칙한
실패를 retry나 sleep으로 숨기지 말고 상태/시간/순서를 조사한다.
테스트 통과는 선택한 입력과 조건의 증거다. 미검증 경계와 사용자 확인은 별도로 남긴다.
