# 사용자가 말하지 못한 고려사항 발견

도메인 전문가처럼 생각하되 과제 크기를 자동으로 키우지 않는다. 질문은 다음 형식으로
만든다: 실제 경계 → 가능한 실패 → 왜 지금 관련되는가 → 확인할 증거 → 최소 대응.

## 조사 순서

1. 원자료와 실제 사용자 흐름을 본다. 이름만으로 구조를 추정하지 않는다.
2. 결과 의미를 바꾸는 항목과 단순 구현 취향을 구분한다.
3. 코드/데이터/문서에서 확인할 사실은 직접 조사한다.
4. 업무 의미·허용 손실·우선순위는 추천안과 대안을 포함해 사용자에게 묻는다.
5. 결정이 비싸거나 가역적이지 않으면 작은 측정·prototype으로 불확실성을 줄인다.

## 주요 경계 질문

| 경계 | 질문 | 실제 실패 |
|---|---|---|
| 입력/정체성 | 한 행/이벤트는 무엇인가, 키가 유일한가 | JOIN 증폭, 중복 저장 |
| 시간/순서 | 사건 시각인가 수신 시각인가, 경계 포함은? | 미래 누수, 누락/이중 집계 |
| 수치/단위 | 비율 분모, 통화/백분율/단위, 정밀도는? | 그럴듯한 잘못된 수치 |
| 상태/재시도 | 완료는 언제 확정되는가, 재실행은 안전한가 | 부분 결과, 중복 부작용 |
| 자원 | 입력/중간 결과 크기, 동시 요청 수, 병목은? | OOM, 시간 초과 |
| 권한 | 누가 누구의 자료를 읽고 바꾸는가 | 사용자 간 자료 노출 |
| 관찰 | 무엇을 보면 성공/실패가 드러나는가 | 빌드만 통과하고 실제 기능 실패 |
| 설명 | 결과가 뒷받침하는 주장 범위는? | 상관관계를 원인으로 단정 |

## 적절한 깊이

로그인 과제에서 JWT를 먼저 결정하지 말고 사용자/권한/세션 수명과 기존 프레임워크를
확인한다. 큰 CSV라면 무조건 분산 처리하지 말고 실제 크기·자료형·필요 열·분할 가능한
연산을 확인한다. 작은 목록 정렬에 고급 인덱스부터 도입하지 않는다.

중요 항목은 보통 1–3개부터 제시한다. “반드시 지금”, “범위 내 추천”, “미래 개선”으로
분류하고 사용자에게 모든 전문 용어를 이해한 뒤 선택하라고 요구하지 않는다.
예: “이 중복을 합치면 실제 생산 수량이 줄 수 있습니다. 배치 ID가 유일해야 하는지
확인하고, 그렇다면 중복을 오류로 표시하는 안을 권합니다.”

관련 분야만 [도메인 색인](../domains/README.md)에서 읽는다.
